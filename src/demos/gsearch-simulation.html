SCENE 01 · THE STARTING POINT

Four seed URLs enter the system.

Seed URLs arrive in the body of POST /api/crawl (on first launch the app seeds itself automatically). These are the only URLs GSearch knows to begin with — everything else is discovered by following links, until crawler.max.pages=500 is reached.

SCENE 02 · THE TASK QUEUE

Pending URLs live in the pool's own task queue.

GSearch has no separate queue object of its own — each pending URL is a task waiting in the ExecutorService queue. crawlUrl() submits new tasks for the links it finds, and the pool's own FIFO ordering is what makes the crawl expand breadth-first rather than following one link chain deep.

SCENE 04 · THE POOL

Now 10 workers share one task queue.

Each card is a worker thread from Executors.newFixedThreadPool(10). Every thread takes tasks from the same queue and submits the links it discovers back into it, so no two workers ever process the same URL — and when the queue empties, they block. Each thread also honours crawler.politeness.delay=1000 before every fetch, and the whole crawl stops at crawler.max.pages=500.
